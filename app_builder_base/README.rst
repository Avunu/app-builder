The engine behind App Builder: it turns records into source files, keeps
the two in agreement, and is honest when they diverge.

A **studio package** is one Odoo addon directory managed as a record.
Everything the builder creates is assigned to a package and written into
it as ordinary ``.xml``, ``.csv`` and ``.py`` files you can review, diff
and commit.

Odoo community has a complete XML *import* path and no export path at
all, so the serializer here is the novel part. Its output is
deterministic by declared rule — attributes in a fixed order, records
ordered by serializer then xmlid rather than by database id, relations
always emitted as ``ref="xmlid"`` — so an unchanged package
re-serializes byte-identically and produces an empty diff.

This module on its own gives you packages, serialization, drift
detection, module reload and adoption of existing models. The builder
UIs live in ``app_builder_model``, ``app_builder_view`` and
``app_builder_ui``.

Usage
=====

Go to **Studio → Packages** and create a package. Its directory defaults
to the first writable entry on the addons path, preferring one named
``custom``.

From then on, anything the builder assigns to that package is written to
disk as you work. The package form shows the generated files, whether
any have been edited by hand, and the git branch they live on.

Three buttons matter:

- **Write to disk** — re-serialize the package. Safe to run at any time;
  an unchanged package produces byte-identical files and no git diff.
- **Reload from disk** — the reverse direction. Re-reads the files into
  the database, which is also how you adopt a hand-edit.
- **Check drift** — compare the files on disk against what the builder
  last generated. A file somebody edited by hand is reported, never
  silently overwritten and never deleted.

Adopt an existing model
-----------------------

New models are already Python. **Studio → Adopt Existing Model** is for
the ones that are not yet: an ``x_`` model built by an older version of
the studio, or one made by hand in Settings → Technical. The records,
the table and its data are untouched; only where the definition lives
changes.

It is lossless because the xmlids Odoo's reflection assigns to a
code-defined model are identical to the ones the studio emitted, and
because the metadata is reclassified rather than deleted. A sandboxed
``compute`` string is promoted to a real method with a real
``@api.depends``.

Adopting requires the package to be installed as a module (Odoo only
imports Python for installed modules) and takes effect once the package
reloads, which ``--dev=reload`` does automatically when the file lands.
It closes no doors: afterwards the model behaves like any other the
builder owns, with the marked block kept in sync and everything outside
it yours.

Production
----------

The editor gates on write access to the package directory. Against a
read-only deployment it disables itself with an explanatory banner
rather than failing: build in development, ship through git, deploy
immutably.

Known issues / Roadmap
======================

Next
----

- **A report is edited as a view, not as a document.** Creating one and
  patching somebody else's both work, and the view editor opens on the
  template — but it edits qweb the way it edits a form, by clicking
  nodes and editing source. What is missing is the document half: a
  powerbox, fields dragged into running text, and dynamic tables. Odoo's
  ``html_editor`` is present in community 18.0, so the parts exist; what
  does not is the mapping from a rich-text edit back to an ``<xpath>``
  in an inheriting view, which is what keeps the edit reviewable.
- **Drag-to-reorder beyond list columns** — form fields between groups,
  kanban card contents. The move operation and the gesture both exist
  now; what each case needs is a sensible answer to "what did you drop
  it *into*". Adding works by clicking, anchored on the selection, for
  the same reason.
- **A new field from inside the view editor.** Adding an *existing*
  field is there; creating one still means the composer, or the New
  Field wizard for a core model.
- **Tags and Lines as features.** Both need a *second* model — a tag
  model with its own access rule, a line model with a many2one back —
  and the app builder makes one. The registry has a place for them; what
  is missing is building the companion, which is a capability rather
  than another entry.
- **A feature that asks for a view still only gets the ones the builder
  can scaffold.** ``Feature.views`` records the intent — Date & Calendar
  wants a calendar, Pipeline stages wants a kanban — and the app builder
  activates what it has scaffolds for.
- **Record rules and automations**, in the composer rather than in the
  technical menus, where they would have the context that makes them
  answerable.
- **Richer filters.** Search filters are generated from a field and a
  condition (is set, is not set, is true, is false). A domain with
  several terms still belongs in the source; a domain *builder* would be
  the way to change that.

Known limits
------------

- **Translated fields carry only their source term.** ``name``, ``help``
  and ``field_description`` are ``translate=True`` jsonb columns, and
  the emitter writes the one string. The fields are in the allowlist, so
  the completeness guard reports clean while every non-source
  translation is dropped. Closing it needs the ``ir.translation``-shaped
  half of the round trip, not another allowlist entry.
- **A field default set through the field editor is not written.** Odoo
  stores it in ``ir.default``, keyed by ``field_id``, and there is no
  serializer for that model — so the default survives on the ``.py``
  path (``FieldSpec.default``) and is lost on the XML one.
- **A value that needs a module is only recorded where a bridge says
  so.** ``_value_depends`` maps a field value to the module that
  contributes it, so a rule using ``review_type="expression"`` pulls
  ``base_tier_validation_formula`` into the manifest. Only the values a
  bridge declares are covered; a selection value from an unbridged
  module still produces a file that loads elsewhere as an invalid value.
- **A module with no bridge loses its fields from generated source.**
  The static coverage test warns, naming each one — ``website`` alone
  adds about a dozen to ``ir.ui.view`` — and fails only for the modules
  the studio itself depends on, which are the ones it is answerable for.
  The runtime guard still refuses to write a record that actually sets
  one, so the data is protected either way; what is missing is the
  bridge, and the warning is the to-do list for writing it.
- **Serializing under ``--dev=xml`` can read the arch off disk.**
  ``_compute_arch`` prefers the file whenever ``arch_updated`` is False,
  so a view whose file and database have diverged serializes the file's
  version. The reload path is what makes that divergence detectable;
  drift detection is the answer to it, not the emitter.
- **A new column needs the class re-imported**, so edits batch behind an
  explicit Apply — one reload per changeset rather than one per field.
  This is not a preference: a ``state='manual'`` field cannot have a
  clean name (a Postgres CHECK constraint, plus
  ``BaseModel._add_field``), so a clean-named field has to be a class
  attribute. Adding a field to a *core* model stays instant, because
  there the ``x_`` prefix is expected anyway.
- **The preview shows the applied state, not the pending one.** A form
  cannot render a field the registry does not have, so the tray carries
  the difference rather than the preview pretending to.
- **Multi-worker deployments cannot reload in place** and are told so
  rather than served badly: the other workers rebuild their registry
  from Python they still hold in ``sys.modules``, so they would rebuild
  against a stale class. Studio editing is a single-process development
  activity; production runs read-only.
- **The inverse of a related list can only be created on a model this
  package defines in Python.** Pointing at anything else needs a
  many2one that already aims back; the picker lists the candidates and
  says so when there are none.
- **Adopting two custom models that reference each other** in the same
  operation is untested; adopt them one at a time.
- **``many2one_reference`` cannot be built here**, because the field
  needs a ``model_field`` companion naming the model its id belongs to
  and the picker has no way to declare one. An existing one serializes
  fine — the companion is read, and the id leaves as an xmlid rather
  than a raw number. ``properties`` and ``json`` are refused outright,
  each with the reason shown in the field picker.
- **The view editor picks nodes from a server-computed tree.** Locators
  are minted server-side against the combined arch, never in the
  browser: the arch a client receives is a per-user projection, with
  nodes removed by group rights and whole subviews grafted in, so a path
  derived from it can be wrong for somebody else.
- **Placement only edits views the package owns.** A field added to a
  model whose form belongs to another module is created but not placed
  automatically — the view editor is where it goes onto somebody else's
  screen, as an inheriting view, on purpose.
- **View edits are live and shared.** A view is data, so there is no
  reload to batch behind and no Apply — an edit is visible to everyone
  immediately. Undo is the counterweight, and it walks back one edit at
  a time; undoing something older would silently discard everything done
  since, so it is refused.
- **A kanban card written with ``t-esc`` cannot be selected part by
  part.** Only a ``<field>`` puts its name in the DOM. Cards the builder
  generates use real fields for exactly this reason; existing ones are
  edited as source, and the editor says so rather than absorbing the
  click.
- **A search view is edited as three lists, not by clicking.** It has no
  rendering of its own — it furnishes another view's control panel — so
  it is edited as searchable fields, filters and group-bys, and
  previewed inside a real list so the menus on screen are the ones being
  edited.
- **A calendar is edited as settings, not by clicking.** It draws events
  rather than fields, so there is no per-node DOM to aim at. What a
  calendar *is* lives in its root attributes, which is what the panel
  edits.
