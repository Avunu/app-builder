App Builder Base

The engine behind App Builder: it turns records into source files, keeps the two in agreement, and is honest when they diverge.

A studio package is one Odoo addon directory managed as a record. Everything the builder creates is assigned to a package and written into it as ordinary .xml, .csv and .py files you can review, diff and commit.

Odoo community has a complete XML import path and no export path at all, so the serializer here is the novel part. Its output is deterministic by declared rule — attributes in a fixed order, records ordered by serializer then xmlid rather than by database id, relations always emitted as ref="xmlid" — so an unchanged package re-serializes byte-identically and produces an empty diff.

This module on its own gives you packages, serialization, drift detection, module reload and graduate-to-code. The builder UIs live in app_builder_model, app_builder_view and app_builder_ui.

Usage

Go to Studio → Packages and create a package. Its directory defaults to the first writable entry on the addons path, preferring one named custom.

From then on, anything the builder assigns to that package is written to disk as you work. The package form shows the generated files, whether any have been edited by hand, and the git branch they live on.

Three buttons matter:

  • Write to disk — re-serialize the package. Safe to run at any time; an unchanged package produces byte-identical files and no git diff.
  • Reload from disk — the reverse direction. Re-reads the files into the database, which is also how you adopt a hand-edit.
  • Check drift — compare the files on disk against what the builder last generated. A file somebody edited by hand is reported, never silently overwritten and never deleted.

Graduate to code

Studio → Graduate to Code converts a visually-built model into an ordinary models.Model subclass in models/*.py that you own outright. The records, the table and its data are untouched; only where the definition lives changes.

It is lossless because the xmlids Odoo’s reflection assigns to a code-defined model are identical to the ones the studio emitted, and because the metadata is reclassified rather than deleted. A sandboxed compute string is promoted to a real method with a real @api.depends.

Graduation requires the package to be installed as a module (Odoo only imports Python for installed modules) and takes effect at the next restart, which --dev=reload triggers automatically when the file lands. It is a one-way handoff: the file is generated once and never overwritten.

Production

The editor gates on write access to the package directory. Against a read-only deployment it disables itself with an explanatory banner rather than failing: build in development, ship through git, deploy immutably.

Known issues / Roadmap

  • The view editor picks nodes from a server-computed tree; true drag-and-drop using core’s data-oe-xpath branding machinery is not implemented yet.
  • Graduating two custom models that reference each other in the same operation is untested; graduate them one at a time.
  • many2one_reference fields cannot be serialized portably (their value is a raw database id) and are refused rather than silently corrupted.

Bug Tracker
