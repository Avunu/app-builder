App Builder: View Editor

Edit views visually. Every change becomes an inheriting view, never a rewrite.

Odoo Studio mutates view arch in place, which is why a Studio-customised database fights every upstream upgrade. Here each edit is emitted as an <xpath> inside a single extension view per (base view, package) at priority=99 — core’s own convention for last-loaded views. The result reads like a patch a developer would have written, survives upstream changes to the base view, and is reviewable in git.

Which view types you can add is not a list this addon keeps. It comes from ir.ui.view.get_view_info(), the registry every module extends when it contributes one — so a site that installs web_timeline sees Timeline, and one running enterprise sees Gantt and Cohort, without this addon depending on any of them. A type the builder has no scaffold for is listed and disabled with that as the reason, because “we cannot make one yet” is true and different from “no such thing”.

Editing happens in a console: full-screen, the real view rendered on a canvas with a real record in it, and a sidebar of Add, View and Properties. Fields, buttons, tabs, groups and columns are dragged from the sidebar onto the view and land exactly where they are dropped; what is already there is dragged to move it, between groups, across tabs, into a kanban card. Because every edit becomes a patch, that works on core screens as readily as on your own. Undo and redo walk the edits back and forward, and every change is on disk before the status pill says so.

The console never asks you for an xpath and never computes one in the browser. The server names every node of the view before it is rendered and edits the node you pointed at, preferring identifying locators (//field[@name='x']) over positional ones (//div[3]) so an edit survives another module extending the same view — and if the view changed under you, the drop is refused, the canvas refreshed, and you are asked to try again rather than have it land somewhere else.

Invalid edits are rejected by Odoo’s own view validator before anything is written, and its message is shown verbatim.

Usage

Open any list, form or kanban and click Studio in the top bar, or pick Edit this view from the cog menu: the console opens full-screen on the view you were looking at, with the record you were looking at in it. Studio → Console opens it with nothing in hand, on the form of the first model your package owns, and the view switcher takes it from there.

The sidebar

  • Add holds three groups of tiles: Components (Tabs, Columns, Group, Separator, Button), New Fields (one per field type the package can make; a type it cannot is shown disabled with the reason) and Existing Fields (every field of the model not yet on the view, searchable). Drag a tile onto the canvas: bars appear between the elements that can take it, the chip names the spot under the pointer — “after Email”, “into Notes”, “at the end of the sheet” — and dropping on nothing does nothing. Resting on a notebook tab while dragging switches to it.

  • View edits the view’s own settings, shows invisible elements when asked, and shows the source of what this package has written for the view together with its recent changes.

  • Properties opens when you click something. It lists the element’s options as label / control rows — the same rows for a core field and one you added — and, for a field, its definition: label, help, required, the values of a selection. A field the package owns is edited in place; a core field shows what it is. Remove from view is at the bottom, and removing a group asks first, with the number of fields it would take.

    A form draws a field’s label only inside a group. A field dropped anywhere else — on the sheet, in a tab, in columns — is given a label of its own (<label for>, the way core’s views do it) so it reads the same; the Show label switch under the Label row takes it away or brings it back, and says so when a label is not shown. The Label row itself renames a field you added in the database; for a field your package defines in Python it relabels this view only, and Edit definition below renames the field itself, on Apply.

Moving is a drag too: pick up a field, a button or a tab and drop it where it should be; a group or a notebook is picked up by the grip on its selection frame, so that a click on it still selects what it holds. List columns reorder by dragging their headings, and take a dropped field between them. In a kanban the drop zones are laid out on one card, outlined as the template’s stand-in, and a drop into any card edits the template — every card follows.

Saving, undoing, applying

Every edit is written when it is made: Saved in the status pill means the inheriting view is on disk. Undo and Redo (Ctrl+Z, Ctrl+Shift+Z) walk the view’s own history, whoever made the edits.

A new field on a model the package owns as Python is the one thing that cannot be immediate: a real column needs the class re-imported. So the drop stages the field and shows it in place as a pending ghost, the pill reads “N pending · Apply”, and Apply places everything staged in one reload. Until then the ghost can be moved, re-anchored or discarded like anything else. On a core model, or on an x_ model, a new field is created and placed at once.

Around the view

The top bar’s tabs — Views, Reports, Automations, Webhooks, Access Control, Filter Rules, Approvals, Edit Menu, New Model — are the studio’s other surfaces scoped to the model in front of you; the ones that are their own screen open with the breadcrumb leading back. The view switcher lists the model’s other views and offers to add the types the package can scaffold. Close returns to where you came from, with the edits already showing.

Known issues / Roadmap

Known limits

  • Inline sub-views are shown but not droppable. A one2many’s embedded list or kanban is rendered on the canvas, but a click inside it selects the field that holds it: its nodes belong to another model and are edited in that model’s own view.
  • A kanban card written with ``t-esc`` has no parts to aim at. Only a <field> puts anything addressable in the DOM; a click on such a part selects the nearest node that is one – the card itself, as a rule – and the parts are edited as source.
  • Models that patch their arch at read time are shown as written. An analytic line’s plan columns are inserted by the model in _get_view() — which Odoo’s own studio also opts out of — and the canvas shows the view as it is defined, not as that model decorates it.
  • Master’s ``card`` view type is not handled yet. From the next Odoo, a kanban may point at a card that lives in a separate view; the node table reserves view_id for it (see FORWARD_COMPAT.md at the repository root).
  • Two consoles on one package are serialised only by the database transaction and the arch-version check: the second drop on a view the first just changed is refused and the canvas refreshed, never written twice.
  • The 19.0 port has been read, not run. Every version difference the console knows is in one file (static/src/console/compat.js), each with the core lines that decide it, and the checklist for the Owl 3 branch is in FORWARD_COMPAT.md; a run against a 19 server is still to do.
